- **Build measured.** The run used the M7 working tree on top of commit `1335559`, which is the code of the M7 commit (the report's build line shows the parent commit because the changes were not committed yet; later runs label such a build `<sha>-dirty`).
- **Frame rate.** The reference display refreshes at 240 Hz and `requestAnimationFrame` follows vsync, so the probe's FPS is capped at 240, not 60. A mean of 239.98 FPS with p99 4.3 ms means every frame (fixed 60 Hz sim steps plus the Pixi render) finished inside a 4.2 ms budget, about four times under the 16.7 ms a 60 FPS target allows. On a 60 Hz display the same build is capped at 60 FPS. The single worst frame was 12.5 ms; no frame took longer than 20 ms.
- **Load over time.** The per-30 s table is flat from the first to the last window: the frame time does not drift as the match fills up. The load is bounded by design: at most 7 ships (the player plus the 6-enemy cap), so with a 1 s interval most spawns after the first few seconds are skipped at the cap, plus the balls in flight and short-lived effects. This is the heaviest match the Options allow.
- **Heap during play.** The JS heap saw-tooths between about 11 and 17 MB as minor GCs run, with no upward trend across the 3 minutes.
- **Memory across matches (PERF-03).** After every return to the menu the DOM node count (224), JS listeners (208), documents (3) and canvases (0) are identical, so nothing from a finished session stays attached. The heap after a forced GC still rises slightly (7.98 MB after cycle 2, 8.62 MB after cycle 5, +8 %, inside the 10 % limit). A 10-cycle diagnostic run with heap snapshots after cycles 2 and 10 ([memory-diagnosis.json](memory-diagnosis.json)) found that it grows in irregular steps of 0.02–0.31 MB per cycle (1.14 MB from cycle 2 to cycle 10), not by a fixed amount per match. About 1.07 MB of those 1.14 MB is V8 compiled code and type feedback (`InstructionStream`, `TrustedByteArray`, `FeedbackVector`, `Code`): the JIT optimising more functions as they run. About 12 KB is Chromium's own per-navigation performance entries (soft navigations, LCP records). App objects and arrays account for only a few KB. There is no per-match app state being retained.
- **Loading.** Pixi and the game code (≈ 175 kB gzip) are downloaded only when Play is pressed. The MSW chunk (≈ 161 kB gzip, most of it MSW itself plus the 24-captain fixtures) is loaded before the first render in every build, because the ranking and history mocks must be ready before any query. It is the price of running the mocks in production.
- **Limits of this evidence.** One machine and one browser (Chromium through Playwright), headed, at DPR 1 and 1920×1080 with a discrete GPU. Not measured: DPR 2–3 phones (the renderer caps `resolution` at 2 for that case), integrated GPUs, Firefox and Safari. The probe measures `requestAnimationFrame` intervals, not GPU time. `performance.memory` is Chromium-only and coarse. The seed is random per run and recorded in the JSON. The run raises the player's health to 100 000 through the dev balance so the ship survives all 180 s; that marks the match `custom` and changes no per-frame cost.
